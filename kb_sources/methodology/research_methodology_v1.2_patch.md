# 方法论 v1.2 补丁

## 发现的盲区

### 盲区1: Phase 0 缺少时间维度

**现象**: v1.1的Phase 0按"类型"穷举源（官网/商店/财报/专利）但漏掉了**历史上发布过**的物料。

**具体遗漏**:
- 2025.05.06: Trailer 2 + 70+张官方截图 + 9角色档案 + 6区域描述 + 故事简介
- 关键信息: Rockstar确认Trailer 2 "全部在基础版PS5上实机录制"——这对图形预期的管理极其重要

**根因**: Phase 0问的是"现在有什么源"而非"这个主题的完整信息发布历史是什么"

### 盲区2: Phase 4 缺少物理/工程反推触发

**现象**: 预载日期(11.12)和发售日(11.19)之间的7天间隔是一个**富含推理价值的工程信号**，但v1.1的"多流认知"没有触发对它的深度推演。

**应该产出的推理链**（仅从"预载11.12→发售11.19"这一个事实）:

```
事实: 预载窗口 = 7天

推理1: 为什么是7天？
  → 典型的3A游戏预载窗口是2-3天
  → 7天是行业最长的预载窗口之一
  → 反推: Rockstar预期文件大小远超常规3A游戏

推理2: 文件大小推演
  → 需要7天下载缓冲 → 目标受众中相当比例使用慢速连接
  → 假设最慢可接受下载时间 = 7天(24小时不间断)
  → 典型慢速连接: 10-25 Mbps
  → 10 Mbps × 7天 = ~740 GB理论最大
  → 但实际不可能24小时下载 → 更合理估计: 150-200 GB
  → 作为对比: GTA V首发~65GB, RDR2~105GB
  → GTA 6推演: 150-200GB (RDR2的1.5-2倍)

推理3: 实体版策略确认
  → PS5蓝光最大100GB, XSX仅50GB
  → 游戏>100GB → 无法放入单张光盘
  → 实体版="盒子里一个下载码" → 已被官方确认
  → 这解释了为什么实体版也在11.12发货——让实体买家也能预载

推理4: 服务器负荷估算
  → 假设首日5000万玩家尝试下载
  → 平均文件大小175GB
  → 总数据量: 5000万 × 175GB = 8.75 EB (艾字节)
  → 7天 = 604,800秒
  → 需要的持续带宽: 8.75 EB / 604,800s ≈ 14.5 TB/s
  → 这需要一个庞大的CDN基础设施
  → 索尼/微软/Rockstar需要提前数月开始协调CDN容量
  → 7天窗口允许负载分散到不同的时间区/天

推理5: 开发时间线反推
  → 11.12预载 → 代码必须在此之前提交到索尼/微软认证
  → 主机认证通常需要2-4周
  → Gold Master(最终压盘版本)锁定 ≈ 10月底
  → 最终bug修复窗口 ≈ 10月中旬结束
  → 这意味着游戏内容在2026年9-10月已基本完成
  → 7-8月是最后的全面QA阶段
  → 与Rockstar印度4月开始QA招聘的时间线吻合

推理6: 首发日服务器策略
  → 预载=提前分发文件=首发日只需解锁
  → 降低首发日CDN峰值负荷
  → 但解锁瞬间仍会有千万级并发请求
  → Rockstar可能在11.19午夜按地理区域分批复解锁
  → 新西兰/澳大利亚先行 → 亚洲 → 欧洲 → 美洲
  → 降低全球同时冲击服务器
```

**这一个事实产生了6条推理链**——涵盖了文件大小、实体策略、服务器工程、开发时间线、首发策略。在v1.1的GTA 6研究中这些全都没产出。

**新增子步骤 Phase 0a — 信息发布历史映射**:

```

YYYY.MM.DD: 事件 — 发布的物料类型 — 可获取的源
```

每个时间节点标识: 已采集/未采集/不适用

### 修补2: Phase 4 加入演绎触发框架

**新增加: 单一事实演绎触发检查清单**

对Phase 2提取的每条central级声明，自动触发以下演绎维度检查:

| 如果声明涉及 | 自动触发演绎维度 |
|-------------|-----------------|
| **日期/时间间隔** | 工程约束反推(存储/带宽/认证/Gold Master) |
| **价格** | 定价策略/竞争定位/消费者弹性/行业影响 |
| **数字(销量/人数/金额)** | 规模反推(基础设施/供应链/团队/时间) |
| **技术规格** | 性能边界(帧率/分辨率/硬件限制) |
| **地理/地点** | 空间推演(地图大小/移动时间/文化内涵) |
| **人事变动** | 组织推演(团队结构/文化变化/战略转向) |
| **合作伙伴/收购** | 战略推演(产品路线图/市场定位/技术整合) |

**使用方式**: 在Phase 4开始时，先将所有central声明过一个"演绎触发扫描"——每条声明触发的维度都标注。确保没有"高价值演绎事实"被遗漏。

### 修补3: Phase 0b — 完整性自检

Phase 1完成后，Phase 2开始前，插入**完整性自检**:

```
自检问题:
1. 时间线上每个标记为"未采集"的节点——是否尝试过获取？
2. 是否有某种类型的物料完全没有代表？（如本次的"Trailer 2同期截图"）
3. 对比同类项目/产品——它们通常发布什么物料？我们漏了什么？
4. 官方渠道的所有子页面是否都被检查过？（官网的/blog /news /media /careers等）
```
