# 自我诊断 · 内核路由失效与修复指引（2026-08-16）

> 写给接手本项目的 agent 开发者。目标：让 agent「干活就走内核」（qra_python 持久内核），
> 把 prime 的「单一持久内核 + 状态跨轮存活」优势真正用起来，而不是每次计算都裸跑
> execute_code / 临时脚本。本文结论全部经源码与运行态核对，非猜测。

---

## 0 · 结论前置

**内核早就建好了，设计意图（D007 指令③「全生命周期计算底座」）也早就定了，但 agent 在实际
session 里仍然不走内核。根因不在「内核能力不足」，而在三层信号断层：**

1. **工具可发现性断层（决定性）**：本会话实测 `tool_describe("qra_python")` 返回
   `{"description": "", "parameters": {"type": "object", "properties": {}}}` —— 空描述、空 schema。
   模型视角下 qra_python 只是一个「没有说明的裸名字」，根本不知道它是持久内核、能跨轮存变量。
2. **路由策略断层**：SOUL.md 是 513 字节的默认人格 stub（无任何 QRA 路由指令）；项目根无
   AGENTS.md / CLAUDE.md；config.yaml 无 system_prompt/instructions 注入。「内核优先」这条规则
   只躺在 D007 ADR 里，模型只有「恰好主动去读了」才知道。
3. **竞争默认值断层**：execute_code / terminal 是 Hermes 内置工具，永远在上下文里、带完整描述、
   天然就是「跑 Python」的默认答案。qra_python 不可见、无描述，于是每次都输给 execute_code。

一句话：**不是模型不听话，是模型「看不见、没被告知」内核该是第一选择。**

---

## 1 · 目标精确定义（先划清边界，避免开发者过度矫正）

「走内核」≠ 所有动作都塞进 qra_python。插件自己的 docstring 已经定义了分工：

> 「内核是『活的数值状态』，文件系统是『跨会话记忆』，两者分工。」

正确路由：

| 动作 | 走哪里 | 理由 |
|---|---|---|
| Python 计算（指标/回测/数据处理/实验/复用函数） | **qra_python** | 变量跨轮存活、dill 快照跨 resume 复活、可写复用函数留内核 |
| 读文件/搜代码 | read_file / search_files | 文件系统是跨会话记忆，读盘不是内核的活 |
| 写文件/落盘产物 | write_file | 同上 |
| 行情/信号/检索/验证 | qra_quote / qra_signal / qra_kb_fts / qra_verify | 各自专职 |

**一句话路由规则（建议直接写进 AGENTS.md/SOUL.md）：**
> 凡是「算」的（写 Python 代码处理数据、算指标、跑回测、做实验），走 qra_python 持久内核；
> 凡是「读/写盘」的，走 read_file / search_files / write_file。连续多步计算必须留在内核里
> 复用状态，禁止拆成 execute_code 一次性脚本重算。

## 2 · 根因详解（含证据）

### 2.1 断层一：deferred 工具面返回空描述（决定性）

- **证据**：本会话 `tool_describe("qra_python")` 实测返回空 description + 空 schema。
- **对照**：插件源码 `.hermes/plugins/qra_python/__init__.py:1244-1285` 明明有完整 schema
  （`{code: string}` + 描述）和 40+ 行的 tool description（1267-1283），`register()` 在
  1288-1305 也把 description/schema 传进了 `ctx.register_tool`。
- **结论**：描述文本在「插件注册 → deferred 工具面（tool_search/tool_describe）」这一段丢失了。
  模型看不到描述 = 永远不主动调用。这是与 D007 P2.5 第 10 项「toolset 发现修复」**同类的
  发现层 bug**，只是那条修的是「工具名不可见」，这条是「工具描述不可见」。

### 2.2 断层二：路由策略只存在于 ADR，未进入运行时指令层

- D007 P2 落地记录第 4 项（雅宁 2026-08-16 指令③）已明确：「定位升级为全生命周期计算底座……
  『把复用逻辑写成函数留在内核里』是首要模式。prime 实证 26h/1229 调用全走单内核零重启支撑该定位。」
  —— 意图早就定了。
- 但这份意图是**决策日志**，不是**运行时指令**。实际每个 session 里模型看到的指令层是：
  - `.hermes/SOUL.md`：513 字节，内容 = Hermes 默认人格首段，无 QRA 路由。已核实这是 Hermes 的
    「人格文件」机制（vendor 源码：从 HERMES_HOME 加载，cron 也继承）。
  - 项目根 `AGENTS.md` / `CLAUDE.md`：**不存在**（HANDOFF 里也没提过）。
  - `.hermes/config.yaml`：无 system_prompt / instructions 字段。
  - `qra_daily` skill：只覆盖日报流水线，只提 signal/quote/kb_fts/memory/verify，**通篇不提
    qra_python**。

### 2.3 断层三：竞争默认值 —— execute_code 每次都赢

- execute_code / terminal 永远在上下文、描述完整、天然匹配「跑一段 Python」的心智。
- 而 execute_code 是**无状态**脚本执行器（每次调用新解释器，变量不跨调用存活），这恰是内核
  要补的短板——但模型没有信号知道这个取舍，于是「眼前有描述清楚的 execute_code」每次都赢过
  「看不见的 qra_python」。

## 3 · 修复方案（按杠杆排序，可直接执行）

### 修复 A（最高杠杆）：补上 deferred 工具面的描述

让 tool_describe / deferred 工具目录透传插件已注册的 description + schema。两个方向：

1. **查修 Hermes deferred 工具面**（推荐先查）：定位 plugin 工具在 deferred 目录里为何空描述，
   让 `ctx.register_tool` 传的 description/schema 一路透传到 tool_describe 结果。改动若在
   vendor 内则违反 D002 铁律 → 走 GRAFT_PATHS 嫁接或上游同步（D009）。
2. **QRA 侧兜底（不动 vendor）**：把内核能力写进「模型一定读得到」的注入层（见修复 B/C），
   即使 deferred 面描述仍空，模型也能从指令层知道 qra_python 是什么、什么时候用。

> 验收标准：新 session 里 `tool_describe("qra_python")` 能返回非空 description（含「持久内核/
> 变量跨调用存活/全生命周期计算底座」等字样）与 `{code}` schema。qra_quote 等其余 5 个工具同理。

### 修复 B（必做）：在运行时指令层写入「内核优先」路由规则

把路由规则从 ADR 提升为**每个 session 自动注入**的指令。两条路二选一或都做：

1. **写 `AGENTS.md`（项目根 `/Users/huyaning/hermes_output/career/tools/quant_research_agent/AGENTS.md`）**
   —— Hermes 会从 workdir 注入项目上下文。内容建议含：
   - 内核优先路由规则（见 §1 那句话）；
   - 内核使用范式：`qra_python({"code": "..."})`，变量跨调用存活，多步计算复用状态，
     复用逻辑写成函数留在内核；`_qra_save()` 主动落盘；
   - 明确「禁止用 execute_code 做需要跨轮复用的连续计算」。
2. **充实 `SOUL.md`**（更根本，因为它无条件加载、cron 也继承）：在默认人格首段后追加 QRA
   路由铁律。SOUL.md 是全局人格，适合放「这条规则对所有 session 生效」的强约束。

> 注：AGENTS.md 适合项目内规则（干活场景），SOUL.md 适合全局铁律（含 cron 日报等无人值守场景）。
> 建议两者都做：SOUL.md 放一条全局路由铁律，AGENTS.md 放完整内核使用手册。

### 修复 C（推荐）：建一个「内核优先」skill，让触发自动生效

skill 会进入模型每轮的技能索引（可见），且能带 scripts/ 模板。建 `qra_kernel_first`（或并入
qra_daily）skill，SKILL.md 含：

- 触发条件：任何「计算/处理数据/跑实验/写代码分析」任务；
- 路由规则（§1 表格）；
- 内核 API 速查（qra_python 参数、qra_runtime 的 harness CRUD / agent_message / qra.run 子代理、
  _qra_save）；
- 反模式清单（连续计算拆成 execute_code 一次性脚本 = 状态丢失 = 反 pattern）。

### 修复 D（收尾）：把 D007 指令③ 落成运行时工件，而非仅 ADR

D007 P2 第 4 项的「全生命周期计算底座」定位，应同步回写进 README 的「内核」行（已有一句）、
AGENTS.md、SOUL.md、skill，确保「设计意图」与「模型实际读到的指令」一致。当前二者是脱节的：
设计层说「内核是底座」，运行时层却没有任何一句话让模型知道这件事。

## 4 · 验证方式（改完如何确认生效）

1. **描述层**：新 session `tool_describe("qra_python")` 返回非空 description + schema。
2. **指令层**：新 session 直接问模型「你要算一个指标，用什么工具？」——应回答 qra_python 并
   说明「变量跨轮存活」；或让它跑一段两步骤计算（第一段定义函数/DataFrame，第二段引用），
   确认它走了 qra_python 且第二步成功复用第一步状态。
3. **行为层（真实链路）**：给一个「算指标 + 回测 + 出结论」的多步任务，观察工具调用序列里
   qra_python 出现且连续复用（而非 execute_code 一次性重算）。可用 `scripts/_smoke_qra_run.py`
   同类 pty 冒烟思路做一条「内核优先」冒烟。
4. **回归**：改动后跑 `scripts/verify_qra.sh --offline`（层 1/2/6），确认没破坏门禁。

## 5 · 边界与诚实声明（别过度矫正）

- 内核不是沙箱（宿主用户权限 + workspace 目录隔离，prime 同款），路由到内核不新增安全面——
  已有 execute_code/terminal 同权。
- 「走内核」针对的是**计算态**；强行把文件读/写也塞进内核是反模式（违背插件自己的分工定义）。
- 内核有 60s 执行超时、256MiB 快照上限、MAX_LIVE_KERNELS=2 的 LRU 池——超长任务或超大状态
  仍应拆分或走 terminal(background)，不要为「走内核」而走内核。
- 修 deferred 描述层若必须动 vendor，务必先查 D002 铁律 + GRAFT_PATHS 登记（D009），不裸改。
