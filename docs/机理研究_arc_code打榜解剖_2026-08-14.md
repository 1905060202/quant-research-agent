# 机理研究：jerber/arc-code 打榜解剖（2026-08-14）

> 背景：社区博主声称用 arc-code 在 ARC-AGI-3 上取得 96.2%、pass@2 99.3%，
> "程序基本是 Claude Code + Opus 5 (high) + 一个动作命令 + 文件系统日志，
> 几乎没有 ARC 特定内容"。雅宁要求研读并评估对 QRA 的价值。
> 方法：clone github.com/jerber/arc-code 至本地，深读全部源码（run.py/act.py/
> rig/*/PROMPT.md/ARC.md/REPRODUCE.md/failure-modes.md/tests/），本文所有结论
> 带 file:line 一手证据。研究执行 2026-08-14。

## 一、96.2% 这个数，先泼冷水

1. **仓库里没有任何 96.2% 的计算数据**。`data/runs/` 只有 6 个示例 session
   （data/README.md:1-4），完整 171 场记录以 release bundle"即将发布"
   （README.md:172-173, 296-299）。96.2 只存在于 README 声称（README.md:6-8）。
2. **分数是逆向公式重建，不是 ARC 官方回执**。score.py:16-18 给出公式
   `level_score=min(115, 100*(human/ours)²)`、`game_score=min(100, Σ(i+1)·level_i/Σ(i+1))`，
   从数据库 actions 表逐局重建。REPRODUCE.md:131-135 明言：24 胜局重建精确，
   第 25 局 lf52（5/10 未完成）属"公式不可靠类"，误差约 ±0.25~1.4 分。
   作者自评："durable claim 是 24/25 胜，不是小数"（REPRODUCE.md:140-141）。
3. **pass@2 = 逐局取最好单次后平均**（score.py:211-225 `best` 命令），
   99.3 = best@2(v2sub, v2rest20, lf52-r1)（REPRODUCE.md:91）。不是"两次并集"，
   是事后 per-game max——不是单次通过率。
4. 结论：**可信的主张是"24/25 局胜 + harness 把同模型裸测从 30.2% 拉到 96.2%"**
   （README.md:3-8），小数点部分别当真。

## 二、"一个动作命令"实际是什么

act.py 仅 4 个子命令 init/do/status/board（act.py:552-575）。
`./act do ACTION1 ACTION6:30,40 --plan "..."` 一次提交**任意长度动作批次**，
顺序执行，某动作改变分数即丢弃剩余（act.py:486-522），全部落盘 logs.txt。
自由度极大：单次 batch 可达剩余全部预算（act.py:476-479），模型可写任意
Python/shell 循环驱动 act（PROMPT.md:61-63）。**act 只是副作用收口点，
不是能力边界。**

## 三、文件系统日志机制（最值钱的 harness 设计）

- act.py 每动作追加一块日志：plan + 动作 + 结果棋盘（hex 渲染）到 logs.txt
  （act.py:138-186）。
- **模型是唯一读者**，通过 grep/sed/Python 按需读回（PROMPT.md:29-38），
  提示词明令"用代码读、禁止打印整盘进上下文"；durable 结论存 notes.md
  （PROMPT.md:40-43）。
- broker 模式下本地日志是 canonical log 的镜像，落后时按 offset 补齐
  （client.py:56-72）。
- 此机制源自 PRO-LONG（README.md:186-189, 317-319）——对抗上下文压缩
  与转录错误的 log-as-memory。

## 四、Claude Code 的角色：子进程，不是模仿对象

- run.py:263-271 以 `create_subprocess_exec` 启动
  `claude -p --output-format stream-json --allowedTools "Bash,Read,Write,Edit,Grep,Glob"`
  （agents.py:68-85）。
- agent loop、上下文压缩、CLAUDE.md 注入全是 CC 原生能力；harness 把
  ARC.md + PROMPT.md 写入 workspace 的 CLAUDE.md（run.py:131-133），
  用 stream-json 记账（agents.py:87-101）。
- **未复用 CC 的 prompt 内容**；同 harness 一键换 Codex（agents.py:149-188），
  证明 loop 设计 CLI 无关。

## 五、"几乎没有 ARC 特定内容"——基本为真

- PROMPT.md 全文无 ARC/网格/颜色/ACTION 名（grep -i arc 仅命中 "search" 词），
  只有通用方法论：1-2 动作验猜测、10-20 批量、错了就推倒重来（PROMPT.md:45-65）。
- 11 行 brief ARC.md 含最小界面事实：64×64 棋盘、坐标、ACTION1-7 惯例，
  注明 "verify rather than assume"（ARC.md:1-11）。
- 颜色图例由 act.py 写进 logs.txt 而非 prompt（act.py:146-148）。
- README.md:300-302 自证：早期含全部界面细节的 prompt 得 97.3（±1 方差内），
  **界面细节对分数≈0**。跨任务可移植只是设计声明，未验证（REPRODUCE.md:165-169）。

## 六、预算/重试/成本

- 预算仅每局 2500 动作硬上限（act.py:39, 476-479）；**无 token 预算、
  无温度/采样参数**。努力度靠 ARCSEC_EFFORT 环境变量（agents.py:62-66）。
- 重试仅网络层指数退避（act.py:35, 222-239）；游戏级靠人工 --resume/--again
  （run.py:401-411, 449-462），lf52 共试 4 次。
- 成本来自 CC result 事件 total_cost_usd（agents.py:95-101）；样本：re86 $21.9、
  lf52-r1 $64.5，cache_read 占绝对大头（lf52-r1: 95.5M token）——实际成本控制
  机制是 Anthropic 的 prompt caching。

## 七、对 QRA 的移植价值评估

### 可移植（4 项）

| # | 机制 | 落点 | 增量价值 |
|---|------|------|---------|
| 1 | **logs.jsonl 时序日志**（act.py:162-186 + PROMPT.md:29-43） | hermes tool executor 加"结果同时追加 workspace/logs.jsonl"包装 + 系统提示加"用代码读日志"一节 | 与 qra_memory（结构化检索）互补：记忆=检索，日志=时序回放 |
| 2 | **审计重判**（audit.py:1-19, 197-218：对存储 event stream 重跑正则，可事后加严） | qra_verify 已有等价物；增量=**重判历史 trace**概念（评分器升级后回放旧会话） | 小；QRA-Bench 评分器演进时可借鉴 |
| 3 | **失败模式学**（docs/failure-modes.md:69-89："记录了不确定性但不做实验就放弃"） | qra_refine 评审门加规则：**每个 unresolved 条目必须配一个验证动作** | 直接提升日报/研报质量 |
| 4 | **broker 密钥隔离 + default-deny fence**（broker.py:1-23, cloud.py:79-101） | 仅 QRA 上云评测时才需要 | 本地无等价物，暂不落 |

### 不可移植（4 项）

| # | 机制 | 为什么不可移植 |
|---|------|--------------|
| 1 | **核心分数来自 Opus 5 权重**——模型自行写出 parser/simulator/search（269 程序 12700 行，README.md:10-21） | 模型差距，非 harness 差距。DeepSeek V4 Pro 的 test-time meta-learning 未知数 |
| 2 | 依赖 CC CLI 的权限/压缩/CLAUDE.md/cost 报表 | QRA 走 anthropic 裸端点零 vendor 改动；引入 CC CLI 违背融合架构 D002 |
| 3 | E2B + Neon + ARC scorecard 闭环 | 绑定特定评测基建 |
| 4 | 成本结构依赖 Anthropic 缓存计费 | DeepSeek 端点计费不同 |

### 诚实边界（最重要）

**96.2% 的贡献主要在模型权重**：harness 只提供 shell + 文件系统 + 单一动作
通道 + 日志记忆，ARC 特定机制（parser/模拟器/搜索）全部由 Opus 每局现建即弃。
harness 的真实贡献只有三点：**log-as-memory**（对抗上下文压缩/转录错误）、
**fence**（分数防作弊可信）、**prompt 方法论**（小验证大批次）。同模型裸测
30.2%→96.2% 说明 harness 有效，但上限由模型决定。~$540 总成本含 4 次 lf52
尝试与 2 次崩溃恢复（README.md:80-81, 221）。

## 八、与 prime 打榜机理的对照（本日第二次研究）

arc-code 与 prime 的 ARC 高分殊途同归，结论一致：
- **prime 95.5%** = Opus 5 权重 ×（单 ipython 持久内核 + 全量 CoT 展示 +
  RLM harness 自改进）。自改进有翻车风险（学会作弊——Factorio RCON），
  QRA 的 qra_verify 比它安全。
- **arc-code 96.2%** = Opus 5 权重 ×（log-as-memory + fence + 通用方法论），
  几乎没有 ARC 特定 prompt。
- **两者共同结论：分数=权重能力为底、harness 为乘数。QRA 能拿的是乘数层，
  拿不到底数层。** 用 DeepSeek V4 Pro 打 ARC-AGI-3 的期望值应以"harness
  乘数有效但底数未知"诚实评估，实测才知道。

## 九、行动项（按优先级）

1. **logs.jsonl 时序日志包装**（可移植项 #1）——Phase 3 嫁接候选，加入 D007。
2. **qra_refine 失败模式规则**（可移植项 #3）——评审门 prompt 加一条规则，
   成本近零收益直接。
3. **不追 ARC 榜**：底数在 Opus 5 权重，QRA 用 DeepSeek 打同榜没有可比性；
   QRA 的差异化在量化研究域（QRA-Bench 30 题已证明域内全对），不在通用推理榜。
