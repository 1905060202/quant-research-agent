## 一、一句话结论

**推荐：prime-agent 做底座。** 但与 v1.0 相比，这次推荐带五条硬性修正（强制隔离、成本预算化、W2 TS spike、Hermes 证据更正、翻盘触发器），并明确承认：**Hermes 从"备选"升格为"几乎平级的第二选项"**，胜负手只剩你对"完整体"的定义。

三个理由（修正后）：

1. **你的量化工作流已经在 prime 上跑通了**——本机 prime 里有 69 条全局记忆、20 个技能，quant-system / a8-trading / investment-report 每天指挥真实的猎豹量化脚本。【本机实测】但 v1.0 把这条说过了头，审计抓出两个问题：其一，prime 本机实例模型仍是 deepseek-v4-flash，不是 pro（我误把 Claude Code 的 settings.json 当成了 prime 的）；其二，"记忆已经长在 prime 里"与"QRA 实验必须隔离生产"互斥——隔离之后记忆只能是**复制同步进实验实例**，不能共享写入。所以这条理由降级为："兼容性由每日生产运行证明，量化记忆资产可复制迁移"。【本机实测+审计核验】
2. **Hermes 的 DeepSeek bug 簇其实早已闭环**——v1.0 说"本周仍活跃"，审计逐条核查 GitHub API：6/9 个相关 issue 在 2026 年 4 月已关闭，其余两个是维护/特性任务（替换 0813 快照、适配峰谷定价），不是 bug。本机复核最新源码：message_sanitization.py 已内置 reasoning_content 回传策略（reasoning_echo_family 系列函数）。【审计核验+本机实测】这条曾是 v1.0 反对 Hermes 的最重武器，现已失效，本文据实删除。Hermes 现在的真实代价是别的（见第四节）。
3. **项目自身的历史教训**——v1 到 v7 五轮推倒重来，最后一次连"已实现的组件"都不在磁盘上。【本机实测】杀死这个项目的从来不是底座不够好，而是架构野心跑赢了验证。prime 是离"真跑通 + 真评测 + 真开源"最近的一条路。这一条审计攻击后依然成立。

**修正后的诚实定位**：prime 赢在「落地距离 + 自我迭代机制 + 官方技术栈复刻」，Hermes 赢在「token 成本 7.3 倍便宜 + 进程内 Python + 记忆系统最强 + '真做了一个 agent'的叙事」。如果你听完第五节后认为 prime 的 SKILL.md-only 路线又是"简化版"，那就选 Hermes——这正是翻盘触发器的第一条，不是客气话。

## 二、先把三个候选说成人话

**Hermes（NousResearch，23 万星，周更 tag v2026.8.13）**
社区最大的 Python 全能 agent。记忆系统是三者最强：SQLite 全文检索（中文 trigram 分词）、记忆分层管理、自动后台整理、字符预算。【源码验证】DeepSeek 适配的 bug 簇已于 2026-04 闭环，当前源码内置 reasoning_content 回传策略。【审计核验+本机实测】它的真实代价是：3.2 万 open issue 的洪流、全部依赖 `==` 锁定的改造阻力、核心 cli.py 单个文件 895KB。

**prime-agent（PrimeIntellect，约 1.57 万星，repo 5 月创建、8 月 5 日发布 v0.7.0、已 42 个 release）**
你自己每天在用的生产 harness。核心机制两条：RLM（把上下文当 Python 变量、把子 agent 当函数调用）+ 持续自我改进（评审双门 + 回滚）。TS 是核心（34.9 万行），Python 只是执行器壳（4 千行）——**但 QRA 可以完全不碰 TS**，原因见第六节。【本机实测+源码验证】

**deepseek-harness（DeepSeek 官方，8 万星，2026-08-13 公开发布）**
架构最先进：事件溯源（一切行为都是可回放的事件日志）、一切皆插件、Agent Notes 制度（545 条工程决策存档）。【源码验证】是 rc 版，官方明牌警告必有破坏性变更。补充一条 v1.0 漏掉的路：官方提供 MCP 零代码桥（@deepseek-ai/dsh-mcp-client），Python 侧可用 FastMCP 服务器接入，不是只有 TS 插件一条路。【源码验证】

## 四、四条决定性新证据（v1.1 修正版）

**① 本机 prime 已经在生产——"不重复造轮子"的现实基础（降级表述）**
~/.prime/agent 实况：settings.json 默认 deepseek-v4-flash + xhigh 思考（**不是 pro**，v1.0 写错）、harness 全局记忆 69 条、20 个 SKILL.md 技能（quant-system / a8-trading / deep-research / investment-report / quant-es-sop 全是量化体系）。【本机实测】QRA 需要的"用户偏好/历史结论/验证卡历史"记忆层有现成资产可复制。但生产实例本身**不能当实验场**（见第八节强制隔离），记忆以复制同步方式进 QRA 实验实例，生产与实验互不污染。

**② Hermes 的 DeepSeek bug 簇已闭环——v1.0 此条证据撤回**
v1.0 声称"reasoning_content 回传 400 错误 bug 簇本周仍活跃、横跨十几个 issue"。审计逐条核查：所引 6 个 issue（#15679/#15353/#16135/#15717/#16388/#15748）全部于 2026-04 关闭；#85388 是特性请求（峰谷定价适配），#85185 是维护任务（替换 V4 Pro 0813 快照），#85896 是 08-13 新开的 cron 卡死 bug——与 QRA 的多轮工具调用负载面无关。本机复核 HEAD 源码：agent/message_sanitization.py 已实现 reasoning_echo_family 回传策略（含 policy 单一 owner 注释）。【审计核验+本机实测】**结论：DeepSeek 兼容性不再构成选 Hermes 的障碍。** 剩余的 0813 快照替换、峰谷定价适配，是三个底座都要做的事（prime 的 model-registry 同样要更新快照版本）。

**③ DeepSeek 官方押注自家 dsh——但这恰恰是"不选它做底座"的理由**
DeepSeek 官方文档写明：V4-Flash 的 Code Agent 基准就是用 DeepSeek Harness minimal mode 测的。【网络信息·官方文档】官方栈兼容零成本，这是真的。但你的战略是"**基座能力不贬值、垂直优势在我手里**"——底座选模型厂商自家 harness，等于把地基打在别人随时可能改道的路上（dsh 官方自己承诺破坏性变更）。第三方 harness（prime/Hermes）反而是"模型无关"的，换模型不换底座。**官方栈适合做 QRA-Bench 的对照组，不适合做你的地基。**此条审计未撼动。

**④ 项目历史教训：架构野心是唯一的敌人**
v1→v7 五轮推倒重来；v6 声称"已实现"的 8 个组件（kernel_state/events/agent_loop/hooks/kb_fts/registry/bridges）在磁盘上一个都不存在，只有 data/ 里的运行轨迹残留。【本机实测 vs 文档声称矛盾】这个教训的推论很直接：**选底座 = 选风险结构，不是选纸面能力。**离验证最近的路优先。此条审计未撼动。

## 七、交接文档遗留问题，逐个裁决

**① "已实现"的 8 个组件不在磁盘——要不要找回？**
**不找回。** 那些组件正是"简化版"的残余，用户的指令是推倒重来。底座的原生能力（prime 的评审门/harness/kernel-state）直接替代它们的全部功能，找回来反而是把旧债背回新架构。

**② LangGraph/LangChain/AutoGen 的 JD 覆盖与四仓库底座路线冲突——谁裁决？**
**底座不负责 JD 覆盖，JD 框架轨道单独走。** 理由：
- JD 明确列 LangGraph/LangChain/AutoGen，这是转岗硬通货，不能丢；【文档声称】
- 但 2026 年面经显示，这类岗位实际考的是"能讲清技术取舍"（checkpoint 持久化、失败节点补偿、RAG 混合召回+重排+MRR、Workflow 约束 Agent），不是"你用了哪个库"。【网络信息·中】

5. prime 上游破坏性变更且跟不动。
