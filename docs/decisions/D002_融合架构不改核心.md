# D002：融合架构——嫁接不改核心循环

- 状态：accepted
- 日期：2026-08-14

## 背景

底座拍板后（D001），如何把 QRA 需求（行情/信号/KB/记忆/验证/日报/评审门）落到 Hermes 上。
直接改 vendor 核心 = 上游更新即冲突、审查成本爆炸；只写 SKILL.md = 完整体不达标。

## 决策

Hermes 骨架 + grafts：所有 QRA 能力以插件（.hermes/plugins/qra*/）形式嫁接，
走官方注册协议（register_tool / memory.provider / spawn 兼容钩），vendor 零改动。

## 备选项

- fork 改核心：违背 D001 的完整体定义方向（不是"能改就改"，是"不该改的不改"）
- 纯技能层：评审门/记忆 provider/verifier 都需要 hook 能力，SKILL.md 形态接不住

## 后果

- 上游 hermes-agent 更新可无损跟进（vendor 独立 git）
- 能力边界 = 官方协议边界：sync_turn 空操作、fork 记忆走 MEMORY.md、review fork 不落库
  ——这些都是上游有意设计，QRA 顺从而非对抗
- 开源时 vendor/ 以 submodule 或引用声明处理，不混入本仓
