## 二、qra_signal 设计

- 数据源：`~/hermes_output/quant/latest_signal.json`（猎豹管道生成，**不重算信号只做可信摘要**——不重复造轮子）
- 输出：market_score / market_sentiment / regime / HOT-COLD 板块榜（top_n 裁剪 1-20，防 51+43 全榜灌爆上下文）/ 个股排名查询（code 参数）

## 三、qra_kb_fts 设计

- 检索策略：查询 ≥3 字符 → trigram MATCH（中英文子串通吃，CJK 分词友好）；短查询或 MATCH 无结果 → LIKE 子串兜底
- 只读连接 `file:?mode=ro`；limit 钳制 1-10；snippet 高亮带出处 doc_name

## 四、本轮踩的三个坑（全部实测发现）

1. **外部内容表索引假阳性**：`SELECT COUNT(*) FROM fts_table` 数的是内容行（永远等于 documents 行数），看起来"同步了"其实 MATCH 恒空。且本环境（SQLite 3.51/Python 3.12）**不自动创建同步触发器**，INSERT documents 根本不进索引。修法：显式 `INSERT INTO fts(fts) VALUES('rebuild')` + 真实 MATCH 探针验证。
2. **snippet 列索引**：旧库是两列表（doc_name, chunk），snippet 列索引 1 指 chunk；重建为标准外部内容模式后 fts 表只有 chunk 一列，索引 1 直接 `InterfaceError: column index out of range`。单列表必须用 0。此错发生在 dispatch 层才暴露——之前 trigram 路径空索引时这段代码从未真正执行过。
3. **MATCH 探针撞特殊字符**：取 chunk 前 3 字符当探针，撞上 "###" 直接 `fts5: syntax error`。修法：regex 提取 `[一-鿿A-Za-z0-9]{3,}`。

## 五、四层验证证据

1. **单元**：build_kb.py 探针 `MATCH('001') → 2 条 ✅ 索引生效`；直接验证 '定价错误'→4、'GTA'→74
2. **dispatch**（registry 层，5 案例全过）：
   - `定价错误` → hits=4, method=trigram, `<b>` 高亮正常
   - `GTA` → hits=3, method=trigram
   - `范式`（短词）→ like_fallback
   - `量子纠缠不存在的词` → hits=0 + 诚实提示
   - 缺参数 → 诚实报错
3. **e2e**：`run_qra.sh -z "先用 qra_signal 查今天热度最高三个板块，再用 qra_kb_fts 查「定价错误」记录，各一句话报告"` → 报告"玻璃玻纤 0.85 / 其他电子Ⅱ 0.832 / 基本金属 0.824"与真实信号一致；KB "4 条，来自 how_cc_hermes_should_work.md 与 research_methodology_v1/v4.md"与真实库一致
4. **state.db**：rowid 67（signal 摘要含 is_stale）、68（kb_fts 空参数→诚实报错→重试的自恢复）、70（kb_fts trigram 命中 4）——真实会话内调用
