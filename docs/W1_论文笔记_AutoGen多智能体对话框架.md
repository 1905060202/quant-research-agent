# 论文精读：AutoGen——多智能体对话框架（arXiv 2308.08155）

> W1 清单 item 5（补）。Microsoft，2023-08，COLM 2024 录用。
> 精读目的：这是 AutoGen W3-4 mini 项目的理论底子，读懂了才不是跑 demo。

## 一句话

**把"多智能体协作"抽象成"多智能体对话"**：Agent 之间不再靠一张状态图连边，而是像人一样开会——说话、听、回应，直到达成一致或达到终止条件。

## 核心抽象：ConversableAgent

所有角色都是同一个类：planner、coder、reviewer、工具执行者、**人类**——统一接口，差异化来自注入的角色定义 + 回复策略 + 工具集。两个好处：

1. **统一接口**：编排复杂度不随角色数爆炸，新增角色=新增实例
2. **可组合的专用化**：reviewer 可以只输出缺陷报告（严格约束注入），天然适合我们 QRA 里的评审门

关键设计——**reply 可以是四种东西之一**：LLM 调用 / 工具调用 / 确定性函数 / 人类输入。这就是"human-in-the-loop 是一等公民"的来源：人类 proxy 在检查点介入（批准、异常处理），常规工作自动跑。

## 会话编程：自然语言 + 代码双通道

流程控制可以写在对话里（"你检查完再交给我"），也可以写在代码里（transition 函数、max_round、termination 条件）。对照我在 QRA 里写的 agent_node：max_rounds=3 的强制汇总——那就是 hand-rolled 的 termination 条件，AutoGen 把它做成了框架能力。

## 对我最有价值的三个判断

1. **图式编排 vs 对话式编排不是二选一**。LangGraph 显式边（我知道每一步去哪），AutoGen 会话流（我看上下文决定下一步）。量化研究这种"分析师查数据→研究员查文档→汇总出结论"的角色分工，对话式更自然；而严格的 pipeline（数据采集→验证→入库）图式更安全。这也是 JD 面试能讲的差异化深度：什么时候选哪个。
2. **多智能体不等于免费的正确性**。论文社区review的提醒很实在：多 agent 放大 token 成本和时延，必须配确定性停止条件 + 沙箱 + 成本护栏。QRA 的评审门（拒绝→"Nothing to save."）和 qra_verify 的 claims 账本就是这个思想的手工版。
3. **审查者模式是最便宜有效的多智能体用法**：不是堆 agent 数量，是给 agent 不对称的权限和约束。主项目 fork 审查（评审 fork 消息不落库、拒绝零写入）与此同构。
