## 二、评审门移植（qra_refine）

### 先纠正记忆

prime 0.7.2 **不是字面意义的"双评审门"**（已核对源码 `/opt/homebrew/lib/node_modules/prime-agent/dist/` refinement.js），实际是三段流水线：①LLM 评审门 `reviewAutoRefine`（准入判断 shouldRefine：只放行跨会话可复用教训，拒绝一次性噪音/瞬时工具输出/无据假设）→ ②LLM 提案 `planRefinement` → ③程序化校验 `applyRefinementProposal`（白名单校验 + 基线快照比对"规划期间条目被改=拒绝"）。

hermes background_review 已具备 ②的对应物（fork 生成审查输出）与 ③的对应物（read-before-write 守卫 + 所有权守卫）。**缺失的是①准入门**——hermes 技能评审偏"主动多存"，prime 的门偏"宁缺毋滥"。qra_refine 移植的就是①。

### 嫁接方式（vendor 零改动）

- 嫁接点 = 官方兼容钩：`spawn_background_review_thread` 用 `getattr(agent, "_XX_REVIEW_PROMPT", 模块常量)` 取提示词；新 agent 走模块常量。
- qra_refine 在 `register()` 时把 `_MEMORY_REVIEW_PROMPT` / `_SKILL_REVIEW_PROMPT` / `_COMBINED_REVIEW_PROMPT` 三个模块常量重写为"**评审门前缀 + 原版正文**"：
  - 第一步准入判断，默认拒绝；放行条件=用户纠正会复发的风格/流程/格式问题、会话发现可复用技巧/工具用法/新知识、已加载技能或记忆有错需修正；必须拒绝=一次性任务叙事、瞬时工具输出、环境性失败、未验证假设、半成品。
  - 拒绝 → 终答只能是 "Nothing to save."，不调工具；放行 → 第一行 "GATE: true - 理由"，再执行原版指令。
  - 冲突裁决条款：门管"存不存"，原版管"怎么存"。
- 幂等（重复 register 不重复包裹）、上游若重命名常量则启动自检告警。

### 发现与决策（都未动 vendor）

- **技能所有权守卫**：后台策展只能改 curator-managed 技能；用户自建技能须一次性 `hermes curator adopt qra_daily` 选择加入。已执行 adopt（usage 记录在 `.usage.json`，已 gitignore）。不 adopt 的话门的放行永远落不了盘（C 会话实测）。
- **fork 记忆写入落内置 MEMORY.md**，qra_memory.db 零副作用——上游 skip_memory 有意设计（防止 harness 提示词泄漏进外部 provider）。MEMORY.md 每次会话加载进系统提示词，评审教训不丢。
- **.gitignore 陷阱**：`.hermes/skills/` 把目录本身也忽略了，后面的 `!` 例外永远不生效（git 不下降进已忽略目录）。改为 `.hermes/skills/*` + `!.hermes/skills/qra_daily/`。W3 时 qra_daily 实际上没被跟踪，本次修复。
- 上游守卫链完整保留：pinned / external_dirs / protected builtin / hub-installed / 非 curator-managed 全拒。
